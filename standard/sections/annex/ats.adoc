== Abstract Test Suite

This annex defines one abstract test per requirement (`/req/` item) in Clause 6 (Functional
Requirements) and Clause 7 (Non-functional Requirements), grouped by conformance class as defined in
<<_conformance>>. A system claims conformance to a named conformance class by satisfying all abstract
tests within that class. Conformance is self-declared; this specification does not define a certification
body or third-party accreditation process. Recommendations (`/rec/` items) are not tested for
conformance; they are listed for completeness in the Recommendations register at the end of this annex.

Each abstract test is identified by a `/conf/{class}/{test-id}` URI mirroring the requirement's
`/req/{class}/{id}` URI. A requirement with lettered parts (A, B, …) is verified by a single test whose
Test method has one numbered step per lettered part, in the order the parts appear in the requirement. A
requirement expressed as an unlettered Statement with a supporting bullet list is verified by a single
test whose Test method covers every bullet, consolidated into fewer steps where several bullets describe
facets of one observable behaviour.

Test method steps are implementation-neutral: they reference configuration, documentation, or observable
system behaviour, and assume no specific database, framework, or user-interface technology. A third-party
assessor with access to the system under test, but not its source code, should be able to execute every
step. Where a requirement's Note narrows its applicability or clarifies its interpretation, the test
method reflects that constraint.

Test type is one of:

- **Inspection**: review of system documentation or configuration.
- **Demonstration**: operating the system and observing its behaviour.
- **Execution**: exercising the system with an automated test tool. Used only where a requirement is
  machine-verifiable without assuming implementation technology (e.g. validating an API response or
  export format against a published schema).

A test may use more than one type across its steps where a requirement genuinely needs both (for example,
Inspection of documented configuration followed by Demonstration of the resulting behaviour).

=== Conformance Class: Core

[[conf_core_data_model]]
==== /conf/core/data-model

[cols="1,4"]
|===
|Abstract test|/conf/core/data-model
|Requirement|/req/core/data-model
|Test purpose|Verify the observation data model captures all fields required by the requirement for both fixed and mobile observing platforms.
|Test method a|
1. For a fixed station, identify a stored observation and confirm the record includes: station and sensor identification, observed element/variable, observation value and unit of measure, quality flag status, observation timestamp (including time zone information), geographic location, and provenance metadata.
2. For a mobile platform with no fixed coordinates, identify a stored observation and confirm its geographic location is recorded per-observation rather than derived solely from station metadata.
3. Confirm each field identified in steps 1–2 is independently retrievable through the system's query or export interface.
|Test type|Demonstration
|===

[[conf_core_observation_storage]]
==== /conf/core/observation-storage

[cols="1,4"]
|===
|Abstract test|/conf/core/observation-storage
|Requirement|/req/core/observation-storage
|Test purpose|Verify observation records persist independently of the ingesting session.
|Test method a|
1. Ingest a test observation and record an identifier or set of filter criteria sufficient to retrieve it again.
2. In a subsequent, independent session (following a system restart where one can be arranged with the assessor, or otherwise after an interval agreed with the assessor), retrieve the observation.
3. Confirm all field values match those originally submitted.
|Test type|Demonstration
|===

|Test purpose|Verify observations can be retrieved filtered by station, spatial extent, time period, element, and quality control status.

1. Retrieve observations filtered by a single station identifier and confirm only that station's observations are returned.
2. Retrieve observations filtered by a geographic bounding box or polygon and confirm only observations from stations within that extent are returned.
3. Retrieve observations filtered by a start and end timestamp and confirm only observations within that period are returned.
4. Retrieve observations filtered by observed element/variable and confirm only observations of that element are returned.
5. Retrieve observations filtered by quality control status and confirm only observations matching that status are returned.
|Test type|Demonstration
|===

|===
|Abstract test|/conf/core/metadata-retrieval
|Requirement|/req/core/metadata-retrieval
|Test purpose|Verify station and sensor metadata can be retrieved filtered by identifier, spatial extent, administrative boundary, classification, element capability, operational status, and temporal validity.
