== Conformance

This specification defines the following conformance classes corresponding to the functional capabilities
of a Climate Data Management System:

- **Core** (Required): Foundational observation storage and retrieval, provenance metadata management,
  and basic station and sensor metadata storage. This class provides the data management foundation on which all other
  conformance classes depend.
- **Observations Quality Control** (Required): Climate-specific QC procedures including range, temporal, spatial, and climatological checks
- **Data Ingestion** (Required): Multi-format data import, validation, and normalization
- **Data API** (Required): Standards-based data query, retrieval, and distribution interfaces
- **Basic Climate Computation** (Required): Computation of derived meteorological variables and summary
  statistics from quality-controlled observations. Homogenization support is recommended but not required
  for conformance to this class.
- **Data Rescue** (Optional): Digitization workflow for historical paper records including imaging and data entry
- **Metadata Management** (Required): Advanced station and element metadata management including WIGOS compliance,
  complete station history, discovery metadata, and metadata quality validation
- **User Interface** (Required): Interactive visualization, data review, and quality control validation capabilities
- **Climate Products** (Recommended): Production and publication of standard climate products and indices
- **Processing Automation and Scheduling** (Recommended): Scheduled and automated execution of routine data processing workflows


[NOTE]
====
The classification of conformance classes as Requirement, Recommendation and Permission aligns with the
Required, Recommended and Optional classifications respectively from the _Climate Data Management System Specifications_ (WMO-No. 1131).
Required classes must be implemented for a system to be considered
conformant. Recommended classes should be implemented where operationally feasible. Optional classes
may be implemented based on specific organizational needs.
====

Non-functional requirements classes (Performance and Scalability, Reliability and Availability, Security,
Usability, Maintainability, Interoperability, Data Governance) are Required.

=== Conformance class definitions

Each conformance class corresponds to one requirements class defined in Clause 6 (Functional
Requirements) or Clause 7 (Non-functional Requirements), identified by the URI conventions defined in
Clause 5 (e.g. `/req/core` → `/conf/core`). Recommendations (`/rec/` items) that appear within a class do
not affect that class's conformance status, whether the class is Required, Recommended, or Optional; see
<<abstract-test-suite>> for how Recommendations are treated in testing.

A conformance claim for a dependent class requires a conformance claim for every class it depends on,
transitively (per each class's Dependency row above). For example, a claim for `/conf/climate-products`
requires claims for `/conf/climate-computation`, `/conf/quality-control`, and `/conf/core`.

Two functional classes — Data API and Metadata Management — depend on the non-functional Security class.
Where a requirements class depends on a class from a different part of this specification (functional or
non-functional), a conformance claim for the dependent class SHALL include a conformance claim for the
class it depends on. This applies the same transitive-dependency rule uniformly, regardless of which part
of the specification the dependency crosses into: a system cannot claim conformance to `/conf/data-api`
or `/conf/metadata-management` without also claiming conformance to `/conf/security`.
